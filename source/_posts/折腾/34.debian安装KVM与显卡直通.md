## 背景提要

+ 本来计划通过WSL实现Windows与Linux双持的，但是奈何辣鸡Windows的BUG是在太多，空转都要占用3G内存，放弃该方案
    + [32.WSL安装.md](32.WSL%E5%AE%89%E8%A3%85.md)
+ 安装双系统，Windows的抽风更新我担心会破坏Linux，不采纳
+ 最后只剩下Linux作为宿主机，在Linux里安装Windows虚拟机，且需要实现显卡直通

## 方案

+ 宿主系统是Debian13，不安装桌面，大部分时候使用的是Linux，通过SSH控制
+ Linux安装Docker，Docker再使用显卡，避免弄脏系统
+ 在Linux基础上，通过KVM虚拟机+PCI显卡直通，部署Windows11物联网版虚拟机
+ KVM负责运行虚拟机，libvirt负责调度虚拟机，cockpit负责界面化管理
+ GPU归属不写死绑定，由libvirt hook脚本动态切换
    + Windows开机：从Linux卸载显卡交接给Windows
    + Windows关机：归还显卡给Linux
+ Linux与Windows的防火墙的全放开


```shell
cp /etc/network/interfaces /etc/network/interfaces.bak
# 记下网卡名，如 enp3s0 / eno1
ip -br addr
# 把 enp3s0 换成你的实际网卡名
cat > /etc/network/interfaces <<'EOF'
source /etc/network/interfaces.d/*
auto lo
iface lo inet loopback
# 物理网卡交给桥接，自己不配 IP
allow-hotplug enp3s0
iface enp3s0 inet manual
# 桥接设备，宿主机 IP 落在这里
auto br0
iface br0 inet dhcp
    bridge_ports enp3s0
    bridge_stp off
    bridge_fd 0
EOF
```

### 安装 NVIDIA 驱动

```shell
lspci -nn | egrep -i "3d|display|vga"                         # 查看GPU类型
apt install -y linux-headers-$(uname -r) linux-headers-amd64  # 构建NVIDIA驱动程序的内核头文件
apt install -y nvidia-driver firmware-misc-nonfree            # 安装NVIDIA驱动
```

```shell
# 开启 IOMMU
# `intel_iommu=on` —— 开启 IOMMU，直通的硬性前提
# `iommu=pt` —— passthrough 模式，只对直通设备做 DMA 重映射，减少宿主机性能损耗
# 注意这里没有 `vfio-pci.ids=`，也没有黑名单 nvidia
# 这是刻意的：宿主机要能正常用 nvidia 驱动跑 Docker CUDA，GPU 归属由 hook 脚本动态切换
# 网上很多教程会写死绑定，那样 Docker 就永远用不了 CUDA 了

cp /etc/default/grub /etc/default/grub.bak

sed -i 's/^GRUB_CMDLINE_LINUX_DEFAULT=.*/GRUB_CMDLINE_LINUX_DEFAULT="quiet intel_iommu=on iommu=pt"/' \
    /etc/default/grub

grep GRUB_CMDLINE_LINUX_DEFAULT /etc/default/grub   # 确认改对了
update-grub
reboot
```

```shell
# 重启后验证（五项都要过）

# IOMMU 已启用
dmesg | grep -i -e DMAR -e IOMMU | head -20 | grep 'DMAR: IOMMU enabled'
# 期望看到 "DMAR: IOMMU enabled"

# 中断重映射
dmesg | grep -i -e "Interrupt remapping" -e "IRQ remapping"
# 期望看到 "DMAR-IR: Enabled IRQ remapping in x2apic mode" 之类

# 驱动正常
nvidia-smi
# 期望看到 RTX 3060 和显存信息

# 记录 GPU 的 PCI 地址
lspci -nn | grep -i nvidia
# 典型输出
# 01:00.0 VGA compatible controller [0300]: NVIDIA Corporation GA106 [GeForce RTX 3060] [10de:2504] (rev a1)
# 01:00.1 Audio device [0403]: NVIDIA Corporation GA106 High Definition Audio Controller [10de:228e] (rev a1)
# 01:00.0 和 01:00.1 必须一起直通（显卡本体 + HDMI 音频），只直通一个会导致 Windows 里驱动异常

# 检查 IOMMU 分组
for g in $(find /sys/kernel/iommu_groups/* -maxdepth 0 -type d | sort -V); do
    echo "IOMMU 组 ${g##*/}:"
    for d in $g/devices/*; do
        echo -e "\t$(lspci -nns ${d##*/})"
    done
done
# 在输出里找到含 `01:00.0` 的那一组
```

| 组内情况                     | 	结论                                          |
|------------------------------|-----------------------------------------------|
| 只有 01:00.0 + 01:00.1	       | ✅ 完美，可直接直通                           |
| 还有同一插槽的 PCIe 桥	       | ✅ 一般也没问题                               |
| 混着 SATA / USB / 网卡控制器	 | ❌ 麻烦。整组必须一起直通，会导致宿主机丢硬盘 |

```shell
export EDITOR=vim
virsh dumpxml win11 # 推荐将整个配置输出，丢给AI让AI按照下面的要求改
virsh edit win11
```

```
+ UEFI 固件（Win11 强制要求）
+ 找到 `<os>` 段
    + `firmware="efi"` 是让libvirt自动挑固件
    + `machine` 必须是 `q35`（不能是 `pc-i440fx`），否则 PCIe 直通无法工作
    + boot 的两种语法互斥，不能混用，混了 virsh edit 保存时会直接报错
        + 上面 grep 到 `<boot order='N'/>` 这类 → 不要动 <os> 段，改用调整 order 数字来控制启动顺序
        + 上面完全没有 boot 相关行 → 才在 <os> 里加下面两行 boot
    + 如果 machine 真的是 pc-i440fx 需要改成 q35，注意不能只改这一个字符串
        + i440fx 是 PCI 拓扑、q35 是 PCIe 拓扑，改了之后已分配的 <address type='pci' .../> 全部失效
        + 必须同时把所有 <address> 行删掉，让 libvirt 重新分配

  <os firmware="efi">
    <type arch="x86_64" machine="q35">hvm</type>
    <boot dev="cdrom"/>
    <boot dev="hd"/>
  </os>
```

```
+ TPM 2.0（Win11 安装检测）
+ 在 `</devices>` 前加
    + 24H2 及更新的 IoT Enterprise 已把 TPM 列为可选，但 21H2~23H2 仍要求，加上没成本

    <tpm model="tpm-crb">
      <backend type="emulator" version="2.0"/>
    </tpm>
```

```
+ 模拟声卡
+ 在 `</devices>` 前加
    + 作用是让 Windows 里始终存在一个音频输出设备
    + RDP 断开后台跑导出任务时，剪辑软件不会因 "未安装音频设备" 报错
    + 真正的声音传输走 RDP 重定向
    + 如果 dumpxml 里已经有 `<audio id="1" .../>`，就只改它的 type，不要再加一个，id 重复保存会报错

    <sound model="ich9">
      <audio id="1"/>
    </sound>
    <audio id="1" type="none"/>
```

```
+ 网络必须走 br0
+ 找到 `<interface>` 段，确认 source 是 br0
    + cockpit-machines 创建时默认会挂 libvirt 的 default NAT 网络，Windows 会拿到 192.168.122.x
    + 那样只能靠宿主机端口映射访问，前面配的桥接就白做了，也拿不到独立IP
    + 本文没有停掉 libvirt 自带的 default 网络，留着不碍事，所以这里必须自己确认改过来

    <interface type="network">
      <source network="br0"/>
      <model type="virtio"/>
    </interface>
```

```
+ 关闭内存气球
+ 找到 `<memballoon>` 改为

    <memballoon model="none"/>
```

```
+ CPU 拓扑
+ 例如4核8线程，给6个vCPU，留2个给宿主机
+ sockets × dies × cores × threads 必须正好等于 vcpu 数，对不上 virsh edit 保存时直接报错

  <vcpu placement="static">6</vcpu>
  <cpu mode="host-passthrough" check="none" migratable="off">
    <topology sockets="1" dies="1" cores="6" threads="1"/>
  </cpu>
```

```
+ 不要删除模拟显卡
+ 两处都不要删：virsh edit 里的 <video> 和 <graphics type='vnc'> 段，以及 Cockpit 页面上 Video / Console 设备的删除按钮
+ Cockpit 创建虚拟机时会自带一个 <video> 设备（vga 或 qxl），务必保留它
+ 这是单显卡直通场景下最重要的救援通道：
    + Windows 里会同时存在「模拟显卡 + RTX 3060」两个适配器
    + 桌面渲染走模拟显卡，所以 Cockpit 的 VNC 控制台一直可用，不会失联
    + 3060 作为纯计算卡存在，CUDA / NVENC 正常可用，RDP 看桌面无压力
+ 很多教程会让你直通后删掉video，那样一旦RDP不通就彻底没有入口了
```

    + 把网络位置改为「专用网络」，判为「公用网络」时防火墙会拦 3389
    + 以管理员身份打开 CMD 执行 `powercfg /h off` 彻底关闭休眠

        + 这条同时也关掉了「快速启动」，两者是同一个休眠文件
+ 关机后确认
    + Windows 能正常启停
    + 在局域网内有独立 IP，能从你的电脑 RDP 连上
    + RDP 里声音正常（客户端 → 显示选项 → 本地资源 → 远程音频 → "在此计算机上播放"）
+ 全部通过再进行下一步，这是整个流程的最后一个安全检查点 —— 此后开始动 GPU，出问题排查难度陡增

### 配置 GPU 直通

```shell
#!/bin/bash
#==============================================================
# libvirt hook - GPU 直通自动切换
#   prepare/begin : 自动停止占用 GPU 的容器 → 卸载 nvidia → 交给 vfio
#   release/end   : 收回 GPU → 恢复 nvidia 驱动（容器需手动重启）
#==============================================================

# libvirt hook 的环境变量极简，PATH 必须显式设置，否则找不到 docker
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

VM_NAME="win11"                                   # ← 改成你的虚拟机名
LOG="/var/log/libvirt-gpu-hook.log"
STATE="/var/lib/libvirt/gpu-stopped-containers"    # 记录被停掉的容器
PERSISTD="/var/lib/libvirt/gpu-persistenced-was-active"  # 记录 nvidia-persistenced 原本是否在跑
STOP_TIMEOUT=8                                    # 单个容器停止等待秒数

[ "$1" != "$VM_NAME" ] && exit 0
log() { echo "[$(date '+%F %T')] $*" >> "$LOG"; }
# 日志超过 1MB 自动截断，防止无限增长
[ -f "$LOG" ] && [ "$(stat -c%s "$LOG")" -gt 1048576 ] && tail -500 "$LOG" > "$LOG.tmp" && mv "$LOG.tmp" "$LOG"
#--------------------------------------------------------------
# 判断容器是否使用 GPU（覆盖三种常见写法）
#--------------------------------------------------------------
uses_gpu() {
    local c="$1" req rt env
    # ① --gpus all（现代写法）
    req=$(docker inspect -f '{{.HostConfig.DeviceRequests}}' "$c" 2>/dev/null)
    [ -n "$req" ] && [ "$req" != "[]" ] && return 0
    # ② --runtime=nvidia（旧写法）
    rt=$(docker inspect -f '{{.HostConfig.Runtime}}' "$c" 2>/dev/null)
    [ "$rt" = "nvidia" ] && return 0
    # ③ NVIDIA_VISIBLE_DEVICES 环境变量（更旧的 nvidia-docker）
    #    以 nvidia/cuda 为基础镜像的容器，即使没带 --gpus 也会继承这个变量，
    #    所以排除 void / none 这两个"明确声明不要 GPU"的取值，减少误停
    env=$(docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' "$c" 2>/dev/null)
    if echo "$env" | grep -q '^NVIDIA_VISIBLE_DEVICES=' \
       && ! echo "$env" | grep -qE '^NVIDIA_VISIBLE_DEVICES=(void|none)$'; then
        return 0
    fi
    return 1
}
#--------------------------------------------------------------
# 回滚：把刚才自动停掉的容器重新拉起来
# 只在"移交 GPU 失败、虚拟机不会启动"时调用，避免容器白白被停着
#--------------------------------------------------------------
restore_containers() {
    command -v docker >/dev/null 2>&1 || return 0
    [ -s "$STATE" ] || return 0
    while read -r name; do
        [ -n "$name" ] || continue
        log "  回滚，重新启动容器: $name"
        docker start "$name" >/dev/null 2>&1
    done < "$STATE"
    : > "$STATE"
}
#--------------------------------------------------------------
# 列出当前还绑在 vfio-pci 上的 N 卡设备（显卡本体 + HDMI 音频）
# 直接问 sysfs，不用手填 PCI 地址：地址填错的话，判断会永远返回"已释放"，
# 下面的等待逻辑就形同虚设，而且日志看起来一切正常，极难发现
# 限定 vendor 10de，是为了不误伤同时直通给别的虚拟机的非 N 卡设备
#--------------------------------------------------------------
vfio_nvidia_devs() {
    local d
    for d in /sys/bus/pci/drivers/vfio-pci/0000:*; do
        [ -e "$d/vendor" ] || continue
        [ "$(cat "$d/vendor")" = "0x10de" ] && basename "$d"
    done
}
#--------------------------------------------------------------
case "$2/$3" in
  "prepare/begin")
      log "===== 启动 $VM_NAME：准备移交 GPU ====="
      # ---- 1. 自动停止占用 GPU 的容器 ----
      : > "$STATE"
      if command -v docker >/dev/null 2>&1 && docker info >/dev/null 2>&1; then
          found=0
          for c in $(docker ps -q 2>/dev/null); do
              if uses_gpu "$c"; then
                  name=$(docker inspect -f '{{.Name}}' "$c" 2>/dev/null | sed 's|^/||')
                  echo "$name" >> "$STATE"
                  log "  停止 GPU 容器: $name"
                  docker stop -t "$STOP_TIMEOUT" "$c" >/dev/null 2>&1
                  found=1
              fi
          done
          [ "$found" -eq 0 ] && log "  未发现运行中的 GPU 容器"
      else
          log "  Docker 未安装或未运行，跳过容器检查"
      fi
      # ---- 1.5 等待 GPU 上不再有计算进程 ----
      # 容器进程退出到显存真正归还有延迟，不等的话紧接着 modprobe -r nvidia 会偶发失败
      for i in $(seq 1 15); do
          n=$(nvidia-smi --query-compute-apps=pid --format=csv,noheader 2>/dev/null | wc -l)
          [ "$n" -eq 0 ] && break
          log "  等待 $n 个 GPU 进程退出..."
          sleep 1
      done
      # ---- 2. 停止常驻占用 GPU 的服务 ----
      # 先记一笔它本来是不是在跑，关机时按原样恢复，不要单方面把用户的服务停死
      rm -f "$PERSISTD"
      if systemctl is-active --quiet nvidia-persistenced 2>/dev/null; then
          touch "$PERSISTD"
          systemctl stop nvidia-persistenced 2>/dev/null
      fi
      # ==============================================
      # ↓↓↓ 单显卡专用：有亮机卡可以删掉这整段 ↓↓↓
      # 注意：这里 unbind 掉的 framebuffer 在 release/end 里不会恢复
      #       也就是说第一次启动 Windows 之后，宿主机 HDMI 就不再有画面，
      #       直到重启 Debian。纯 SSH 使用没影响，但要接显示器本地救援时得先重启宿主机
      # ==============================================
      for vt in /sys/class/vtconsole/vtcon*/bind; do
          [ -w "$vt" ] && echo 0 > "$vt" 2>/dev/null
      done
      for drv in simple-framebuffer efi-framebuffer; do
          [ -d "/sys/bus/platform/drivers/$drv" ] || continue
          for dev in /sys/bus/platform/drivers/$drv/*; do
              [ -e "$dev/driver" ] || continue
              basename "$dev" > "/sys/bus/platform/drivers/$drv/unbind" 2>/dev/null
          done
      done
      sleep 2
      # ==============================================
      # ↑↑↑ 单显卡专用段落结束 ↑↑↑
      # ==============================================
      # ---- 3. 卸载 nvidia 模块 ----
      # 逐个卸载并容错。原因：如果其中某个模块本来就没加载，
      # 一条 modprobe -r 带多个模块会整体返回失败，
      # 脚本会误判成"卸载失败"并 exit 1，从而阻止虚拟机启动
      for m in nvidia_drm nvidia_modeset nvidia_uvm nvidia; do
          if lsmod | grep -q "^$m "; then
              modprobe -r "$m" 2>>"$LOG"
          fi
      done
      # 用"还有没有nvidia模块残留"作为真正的判断依据
      if lsmod | grep -q '^nvidia'; then
          log "!! nvidia 模块卸载失败，诊断信息如下："
          log "---- 仍加载的模块 ----"
          lsmod | grep -E '^nvidia|^vfio' >>"$LOG" 2>&1
          log "---- 占用 /dev/nvidia* 的进程 ----"
          fuser -v /dev/nvidia* >>"$LOG" 2>&1
          log "---- 当前运行的容器 ----"
          docker ps >>"$LOG" 2>&1
          log "---- nvidia-smi ----"
          nvidia-smi >>"$LOG" 2>&1
          # 虚拟机不会启动了，把刚停掉的东西还回去，否则容器会一直停着没人管
          restore_containers
          if [ -f "$PERSISTD" ]; then
              systemctl start nvidia-persistenced 2>/dev/null
              rm -f "$PERSISTD"
          fi
          log "!! 已中止启动，请处理上述占用后重试"
          exit 1
      fi
      log "  nvidia 模块已全部卸载"
      # ---- 4. 加载 vfio ----
      modprobe vfio-pci
      log "===== 就绪，libvirt 接管 GPU ====="
      ;;
  "release/end")
      log "===== $VM_NAME 已停止：收回 GPU ====="
      # 等待 libvirt 把设备从 vfio-pci 解绑（最多等 20 秒）
      # 这里必须等：hook 的 release/end 可能跑在 libvirt 归还设备【之前】，
      # 那时急着 modprobe nvidia，模块会加载成功但抓不到卡，
      # nvidia-smi 报"未找到设备" —— 这就是"偶发失败"的主要来源
      for i in $(seq 1 20); do
          left=$(vfio_nvidia_devs)
          [ -z "$left" ] && break
          sleep 1
      done
      if [ -n "$left" ]; then
          # 等超时说明 libvirt 没把设备还回来（虚拟机异常退出、或 hostdev 不是 managed='yes'）
          # 这时必须手动解绑，否则 vfio_pci 卸不掉，nvidia 也抓不到卡
          log "  等待超时，手动从 vfio-pci 解绑: $(echo $left)"
          for d in $left; do
              echo "$d" > /sys/bus/pci/drivers/vfio-pci/unbind 2>>"$LOG"
          done
          sleep 1
      else
          log "  设备已从 vfio-pci 释放"
      fi
      modprobe -r vfio_pci vfio_iommu_type1 vfio 2>/dev/null
      sleep 1
      if modprobe nvidia && modprobe nvidia_uvm; then
          log "  nvidia 驱动已恢复"
      else
          log "!! nvidia 驱动恢复失败，请检查：dmesg | tail -30"
      fi
      # nvidia 模块只认领显卡本体，HDMI 音频功能会停在"无驱动"状态
      # 触发一次驱动重新匹配，让 snd_hda_intel 接回去
      for d in /sys/bus/pci/devices/*; do
          [ "$(cat "$d/vendor" 2>/dev/null)" = "0x10de" ] || continue
          [ -e "$d/driver" ] && continue
          basename "$d" > /sys/bus/pci/drivers_probe 2>/dev/null
      done
      # 按原样恢复 nvidia-persistenced
      if [ -f "$PERSISTD" ]; then
          systemctl start nvidia-persistenced 2>/dev/null && log "  nvidia-persistenced 已恢复"
          rm -f "$PERSISTD"
      fi
      # ---- 提示需要手动恢复的容器（不自动启动）----
      if [ -s "$STATE" ]; then
          log "  以下容器此前被自动停止，需手动启动："
          while read -r name; do
              [ -n "$name" ] && log "      docker start $name"
          done < "$STATE"
      fi
      log "===== 完成 ====="
      ;;
esac
exit 0
```

### 日常使用流程

+ 切到 Windows
    + 浏览器打开 https://IP:9090 → 虚拟机 → win11 → Run → 等 1 分钟 → RDP 连接
    + 使用 CUDA 的 Docker 容器会被 hook 自动停止，无需手动操作
+ 切回 Linux
    + Windows 里点关机（不是睡眠）→ 30 秒后宿主机自动恢复 CUDA
+ 出问题先看日志
    + `tail -50 /var/log/libvirt-gpu-hook.log`
    + `dmesg -T | tail -30`
